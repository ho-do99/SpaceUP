# 백엔드 최소 테이블 정합화 안내

## 작업 목적

실DB와 현재 백엔드 엔티티, Figma v2 사용자·시공사 화면 흐름이 서로 달라 실행 시점마다 Hibernate가 스키마를 자동 변경할 수 있는 상태를 해소했다. 테이블 수를 줄이되 기존 견적·채팅·현장 방문·프로젝트·리뷰 흐름은 유지하는 것을 기준으로 삼았다.

## 최종 구조

- 실DB 테이블 수: 24개에서 25개
- 추가: `apartments`, `floorplan_variants`, `contractor_projects`, `project_checklist_items`, `reviews`
- 제거: `boards`, `comments`, `upload_files`, `schedule_events`
- 적용 SQL: `database/migrations/20260806_05_minimal_schema_alignment.sql`

추가한 5개 테이블은 이미 백엔드 엔티티와 서비스가 사용 중이었지만 실DB에 없었다. 명시적 마이그레이션 없이 `ddl-auto=update`에 맡기면 개발자별 실행 시점에 따라 스키마가 달라질 수 있어 SQL로 고정했다.

제거한 4개 테이블은 적용 직전 모두 0건이었다. `boards`, `comments`, `upload_files`는 현재 대응하는 엔티티·Repository·Controller와 화면이 없고, 이미지는 현재 파일 저장소와 각 도메인의 URL 컬럼으로 관리한다.

## `schedule_events`와 schedule API를 제거한 이유

현재 화면과 코드에는 일정의 성격이 명확히 나뉘어 있다.

- 계약 전 현장 방문: `site_visits`
- 시공 확정 후 공사 일정·상태·완료: `contractor_projects`
- 프로젝트별 진행 항목: `project_checklist_items`

범용 `schedule_events`는 이 두 흐름과 역할이 겹쳤고 데이터도 0건이었다. 프론트엔드에는 `/api/schedules` 호출이 없으며, 시공사 하단의 프로젝트 흐름도 별도 프로젝트 도메인을 기준으로 한다. 따라서 범용 schedule 도메인을 유지하면 같은 일정을 어느 테이블에 기록해야 하는지 불명확해지고 상태가 서로 어긋날 가능성이 더 컸다.

이에 따라 미사용 `domain/schedule` 패키지와 `ScheduleNotFoundException` 및 전역 예외 처리 항목을 제거했다. 현장 방문과 프로젝트 기능 코드는 삭제하거나 다른 API로 강제 전환하지 않았다.

## 담당자가 알아야 할 API 기준

- 견적 확정 전 방문 일정은 기존 `site_visits` 도메인과 `/api/visits` API를 사용한다.
- 견적 확정 후 시공 진행은 기존 `contractor_projects` 도메인과 `/api/projects` API를 사용한다.
- `/api/schedules`는 현재 화면에서 사용되지 않던 중복 API이므로 제거됐다.
- 프로젝트·리뷰 서비스의 업무 로직과 프론트 화면은 이번 단계에서 수정하지 않았다.

- `ddl-auto=update`에서 `validate`로 전환하지 않았다. 남은 마이그레이션이 끝나기 전에 바꾸면 다른 스키마 차이 때문에 팀 실행을 막을 수 있다.
