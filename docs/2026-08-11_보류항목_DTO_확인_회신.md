# 보류 항목 DTO/식별자 확인 회신

작성일: 2026-08-11 (동일자 재검증: `origin/frontend` 실제 코드 최신 커밋 `61d9cdf` 기준 대조 완료)
대상 브랜치: `backend` (push 완료, 커밋 `e1946e7`)

보내주신 1~10번 질문에 순서대로 답합니다. 대부분 이미 구현되어 있어 명세만 확정하면 되고, 9번(`contractorId`)만 실제로 코드에 추가했습니다.

**이번 재검증에서 추가로 확인한 것**: 처음 답변은 백엔드 코드만 보고 작성했는데, 그 사이 프론트에서 `feat: integrate available backend APIs` 커밋으로 실제 API 연동을 상당수 진행하셨더라고요. 그래서 이번엔 각 항목마다 프론트 실제 코드(`origin/frontend` 최신)까지 대조해서 "이미 실제로 연결됨"/"아직 목업"과, 실제로 연결됐을 때 제가 드린 답변과 필드명이 맞는지 확인한 결과를 각 항목 아래 `> 🔍 프론트 대조 결과`로 추가했습니다.

## 1. `PUT /api/member/{memberId}` — `MemberUpdateRequest`

이름/이메일 2개 필드만 받습니다. **phoneNumber/password는 이 endpoint로 수정 안 됩니다** (별도 endpoint, 아래 참고).

```json
{
  "email": "test@test.com",
  "name": "장지선"
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| email | string | 필수 | `@Email` 형식 검증 |
| name | string | 필수 | 최대 20자 |

- phoneNumber 변경: `PATCH /api/member/me/phone` — `{"phoneNumber": "010-1234-5678"}` (변경 즉시 `phoneVerified=false`, 재인증 필요)
- password 변경: `PATCH /api/member/me/password` — `{"currentPassword": "...", "newPassword": "..."}` (신규 추가된 API, 현재 비밀번호 확인 필요)

> 🔍 **프론트 대조 결과**: 이미 실제로 연결되어 있고(`frontend/src/api/memberApi.ts`의 `updateMember(memberId, {email, name})`), Body 타입도 정확히 `{email: string; name: string}`로 일치합니다. 별도 확인 불필요합니다.
> 비밀번호 변경 화면은 사용자/시공사 양쪽 다 아직 버튼이 `disabled`인 플레이스홀더 상태라 실제 연결은 안 됐지만, 위 API를 그대로 쓰면 됩니다.

## 2. `PUT /api/contractors/me` — `ContractorProfileUpdateRequest`

응답 필드 중 `rating`/`reviewCount`/`completedProjectCount`는 말씀하신 대로 서버 관리값이라 **Request Body에 없습니다.** 실제 Request는 아래 6개뿐입니다.

```json
{
  "businessRegistrationNumber": "123-45-67890",
  "companyName": "스페이스업 인테리어",
  "activityRegions": "광주 북구,광주 서구",
  "specialties": "도배,바닥재,조명",
  "portfolioUrl": "https://example.com/portfolio",
  "introduction": "10년 경력의 인테리어 전문 업체입니다."
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| businessRegistrationNumber | string | 선택 | |
| companyName | string | 선택 | |
| activityRegions | string | 선택 | 콤마로 구분된 문자열(배열 아님), 예: `"광주 북구,광주 서구"` |
| specialties | string | 선택 | 콤마로 구분된 문자열, 예: `"도배,바닥재,조명"` |
| portfolioUrl | string | 선택 | |
| introduction | string | 선택 | |

> ⚠️ 현재 검증 애너테이션(`@NotBlank` 등)이 없어 전부 optional입니다(빈 값으로 저장 가능). 있으면 update, 없으면 자동 생성되는 upsert 방식입니다.

> 🔍 **프론트 대조 결과**: `PUT` 저장 API는 아직 연결 안 됐지만(조회 `GET /api/contractors/me`만 연결됨), 프론트 타입(`frontend/src/types/backendContractor.ts`)이 이미 `activityRegions`/`specialties`를 `string | null`로 선언해뒀고, 읽을 때도 `profile.specialties?.split(',')`로 콤마 분리를 하고 있어서 — 콤마 문자열 방식이라는 제 답변과 이미 일치합니다.
> ⚠️ 다만 활동지역/전문분야를 고르는 화면(`ContractorCompanySpecialtiesPage.tsx`)은 다중 선택 UI인데 아직 API 연결이 전혀 없는 상태예요. 나중에 저장 API를 연결할 때 선택한 배열을 `.join(',')`으로 합쳐서 보내야 한다는 점만 미리 참고해 주세요.

## 4. `PUT /api/contractors/me/disclosure` — `DisclosureSettingsUpdateRequest`

말씀하신 대로 프로필 응답의 6개 공개설정 필드를 그대로 Body로 받습니다. boolean이라 필드를 생략하면 `false`로 처리되니 6개 전부 보내는 걸 권장합니다.

```json
{
  "profilePublic": true,
  "contactPublic": true,
  "specialtyPublic": true,
  "regionPublic": true,
  "portfolioPublic": true,
  "availableForConsult": true
}
```

> 🔍 **프론트 대조 결과**: 아직 연결 안 됐는데, **연결하시기 전에 꼭 확인해주셔야 할 게 있습니다.** 프론트 `ContractorVisibilitySettingsPage.tsx`가 이미 만들어둔 로컬 상태 필드명이 백엔드와 다릅니다.
>
> | 백엔드 (`DisclosureSettingsUpdateRequest`) | 프론트 로컬 상태 |
> |---|---|
> | `profilePublic` | `profileVisible` |
> | `contactPublic` | `managerContactVisible` |
> | `specialtyPublic` | `specialtiesVisible` |
> | `regionPublic` | `serviceRegionsVisible` |
> | `portfolioPublic` | `portfolioVisible` |
> | `availableForConsult` | `consultationAvailable` |
>
> 지금 당장 문제되는 건 아니지만(API 호출 자체가 없어서), 나중에 연결할 때 이 6개를 1:1로 매핑해서 보내야 합니다.

## 6. `GET /api/analysis/request/{requestId}/recommended-products` — 응답 DTO

기존 자재 카탈로그(`MaterialProductResponse`)를 그대로 반환하는 건 **아닙니다.** 별도 응답 타입(`RecommendedMaterialResponse`)이 있고, **필드명은 이전에 안내드린 것과 동일합니다** — 백엔드 내부적으로 클래스명만 정리됐고 JSON 필드는 안 바뀌었습니다.

```json
{
  "success": true,
  "message": "추천 상품 조회 완료",
  "data": [
    {
      "productId": 12,
      "productName": "○○ 강마루 A등급",
      "category": "FLOORING",
      "spec": "1850x150x7.5mm",
      "brand": "동화자연마루",
      "vendorName": "동화자연마루",
      "imageUrl": "https://.../floor.jpg",
      "unitPrice": 45000,
      "unit": "박스",
      "quantity": 12,
      "coverageM2": 33.0,
      "amount": 540000,
      "reason": "바닥 노후화 이슈에 맞춘 추천",
      "priority": 1
    }
  ]
}
```

| 필드 | 타입 | 비고 |
|---|---|---|
| productId | number | |
| productName | string | |
| category | string | `FLOORING`/`WALLPAPER`/`LIGHTING`/`KITCHEN` |
| spec | string | |
| brand | string | |
| vendorName | string | **⚠️ `@Deprecated`** — 현재는 `brand`와 같은 값. 앞으로 없어질 예정이니 `brand`를 쓰는 걸 권장 |
| imageUrl | string | |
| unitPrice | number | |
| unit | string | |
| quantity | number | |
| coverageM2 | number | |
| amount | number | 단가 × 수량 |
| reason | string | 추천 이유 |
| priority | number | 카테고리 내 순위(1부터) |

> **[참고]** 이 endpoint에 `theme` 쿼리 파라미터(`MODERN`/`WOOD`/`WHITE`/`MARBLE`, 선택)가 추가되어 있습니다. 필요하면 활용하시고, 안 넘기면 테마 무관하게 추천됩니다.

> 🔍 **프론트 대조 결과**: 이미 실제로 연결되어 있습니다(`frontend/src/api/analysisApi.ts`의 `getRecommendedProducts`). 타입(`RecommendedProduct`, `frontend/src/types/analysis.ts`)도 위 13개 필드와 완전히 동일하고, `vendorName`에 `@deprecated` 주석까지 이미 달아두셨더라고요 — 그대로 쓰시면 됩니다. 추가 확인 불필요합니다.

## 7. `POST /api/quotes/{quoteId}/request-revision` — Body 필드명

세 후보(`message`/`memo`/`revisionRequestNote`) 중 어느 것도 아니고, 실제 필드명은 **`note`**입니다.

```json
{
  "note": "자재비 항목을 다시 확인해주세요.",
  "targetItemIds": [12, 15],
  "requestedAmount": 4500000
}
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| note | string | **필수** | |
| targetItemIds | number[] | 선택 | 수정이 필요한 견적 항목(`ContractorQuoteItem.id`) 목록. 특정 항목이 아니면 생략 |
| requestedAmount | number | 선택 | 희망 조정 금액(원). 특정 금액 요구가 없으면 생략 |

> `targetItemIds`/`requestedAmount`는 이번에 새로 추가한 선택 필드입니다. `note`만 보내도 기존과 동일하게 동작합니다.

> 🔍 **프론트 대조 결과**: 아직 연결 안 됐습니다(`estimateApi.ts`에 `request-revision` 호출 자체가 없고, 수정요청 UI는 전부 로컬 mock 상태로 동작 중). ⚠️ 한 가지 헷갈리기 쉬운 부분: **조회(GET) 응답 쪽**에는 이미 `QuoteResponse.revisionRequestNote`라는 필드명이 프론트 타입에 있습니다. 이건 이 API가 아니라 견적 조회 응답의 필드라 이름이 다른 게 맞습니다 — 저장할 때(POST) 보내는 값은 `note`, 조회할 때(GET) 돌려받는 값은 `revisionRequestNote`로 이름이 다르다는 점만 유의해 주세요.

## 8. 이메일 변경/인증 — 신규 구현 완료

말씀하신 대로 백엔드에 없던 기능이라 휴대폰 인증과 동일한 구조로 새로 만들었습니다.

- `POST /api/member/me/email/verify-code/send` — Body 없음(로그인 토큰만). 응답으로 인증코드 반환(목업: 실제 메일 미발송)
- `POST /api/member/me/email/verify-code/confirm` — `{"code": "123456"}` → 성공 시 `emailVerified=true`
- 이메일 자체 변경은 기존 `PUT /api/member/{memberId}`로 하면 됩니다. **이메일이 실제로 바뀌면 `emailVerified`가 자동으로 `false`로 초기화**됩니다(휴대폰과 동일한 동작).
- `MemberResponse`에 `emailVerified` 필드가 추가되었습니다.

> 🔍 **프론트 대조 결과**: `ContractorAccountSettingsPage.tsx`의 이메일 변경 다이얼로그(`ContractorEmailChangeDialog.tsx`, 발송/확인 2단계 UI까지 이미 구현됨)가 여전히 `throw new Error('이메일 인증 API 계약이 없어 변경을 진행할 수 없습니다.')`로 막혀 있는 걸 확인했습니다. 정확히 이 API를 기다리고 계셨던 상태라, 위 두 endpoint로 그 스텁만 실제 호출로 바꾸시면 바로 동작할 겁니다.

## 9. 사용자 프로젝트 목록/상세 — 식별자 + `contractorId`

- `GET /api/projects/landlord/me` 응답 배열의 `id`는 `GET /api/projects/{projectId}`에 그대로 쓰는 `projectId`가 **맞습니다.**
- **`contractorId`를 `ProjectResponse`에 추가했습니다** (기존엔 `contractorName`만 있었습니다).

```json
{
  "id": 7,
  "requestId": 21,
  "quoteId": 33,
  "requestCode": "REQ-20260811-007",
  "customerName": "홍길동",
  "contractorId": 5,
  "contractorName": "스페이스업 인테리어",
  "address": "광주 북구",
  "status": "IN_PROGRESS",
  "contractDate": "2026-08-01",
  "contractAmount": 5000000,
  "startDate": "2026-08-05",
  "completionDate": null,
  "constructionItems": "도배,바닥재",
  "customerRequest": "빠른 시공 부탁드립니다",
  "checklist": []
}
```

> 🔍 **프론트 대조 결과**: 시공사 쪽(`getContractorProjects`/`getProject`)은 이미 연결되어 있는데, **사용자(임대인) 쪽 `getLandlordProjects()`는 함수만 정의되어 있고 실제로 화면 어디서도 호출을 안 하고 계시더라고요.** `Project` 타입에도 아직 `contractorId` 필드가 없습니다 — 이번에 백엔드가 응답에 추가했으니, 연결하실 때 프론트 `Project` 타입에도 `contractorId: number`를 추가해 주시면 됩니다.

## 10. 사용자 리뷰 작성 — `requestId` 재사용 확인

네, 맞습니다. `ProjectResponse.requestId`를 `POST /api/reviews/request/{requestId}`의 `{requestId}`로 그대로 사용하면 됩니다. 리뷰는 `constructionId` 같은 별도 식별자 없이 `requestId` 하나로만 연결되는 구조이고, 이 부분은 이번에 변경되지 않았습니다. 리뷰 API 추가 구현은 필요 없습니다.

> 🔍 **프론트 대조 결과**: `frontend/src/api/reviewApi.ts`에 `createReview(requestId, {rating, content, keywords})` 함수가 이미 정확한 형태로 만들어져 있는데, 실제 리뷰 작성 화면(`UserReviewFormPage.tsx`)은 아직 이 함수를 안 쓰고 `sessionStorage`에 직접 저장하는 방식으로 동작 중입니다. 화면을 이 API로 바꾸실 때 `requestId`를 `ProjectResponse.requestId`에서 가져오시면 됩니다.

| 번호 | 백엔드 상태 | 프론트 실제 연결 상태 |
