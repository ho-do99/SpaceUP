# SpaceUP DB·연동 전체계획 재수립

## 결론

현재 DB는 Flyway 기준 업무 테이블 25개로 재현 가능하고, 자재업체 기능 제거·복수 시공사 참여·채팅 분리·견적 선택·현장방문·프로젝트·리뷰의 백엔드 골격은 갖춰졌다. 그러나 프론트의 시공사 포털 상당수와 사용자 의뢰 생성 시작점은 여전히 목업이다. 이 상태에서 테이블을 더 만드는 것보다 실제 화면이 API를 호출하도록 연결하는 일이 우선이다.

테이블 수가 처음 공통 17개를 검토하던 때보다 25개로 늘어난 이유는 기능을 임의로 늘린 것이 아니라, 실제 코드와 화면에 이미 존재하던 다중 시공사 참여·현장방문·견적 항목·프로젝트 체크리스트·이미지·인증·설정 등을 분리했기 때문이다. Flyway 관리 테이블 `flyway_schema_history`는 업무 테이블 수에 포함하지 않는다.

## 이번 단계에서 확정한 것

- 자재 카탈로그 `material_product`는 유지한다.
- 자재업체 회원·입점·재고·주문 로직은 제거 대상이며 신규 설계에 포함하지 않는다.
- 사용자는 확정 전 여러 시공사와 각각 채팅하고 견적을 비교할 수 있다.
- 견적 하나를 선택하면 해당 시공사만 `SELECTED`, 나머지는 `CLOSED`가 된다.
- 현장방문도 요청+시공사별로 분리한다.
- 수락 견적→프로젝트→착공→완료 요청→임대인 완료 확인→리뷰 순서를 유지한다.
- 정산은 정책 미확정이므로 구조 변경을 보류한다.
- DB 자동 변경은 Flyway만 담당하고 Hibernate는 검증만 한다.

## 발견한 실제 연결 공백

### 1순위: 사용자 의뢰 생성 시작점

프론트에 `createRequest` API 함수는 있지만 현재 런타임 화면에서 호출하지 않는다. 따라서 `ACTIVE_REQUEST_ID_KEY`도 실제로 저장되지 않는다. 이 연결이 먼저 돼야 이후 AI 분석·이미지 연결·선택 자재 저장이 한 의뢰 ID 아래 이어진다.

### 2순위: 시공사 포털 실 API 전환

시공사 의뢰 목록·상세·방문·견적 화면 다수가 `contractorPortalMockData`와 메모리 Context를 사용한다. 채팅 일부는 숫자 request ID에서만 실 API를 사용한다. 화면을 한꺼번에 바꾸면 담당자 테스트 흐름을 깨므로 페이지 단위로 다음 순서가 안전하다.

1. 의뢰 목록/상세 조회
2. 승인/거절
3. 시공사별 현장방문 일정
4. 견적 임시저장/발송
5. 프로젝트/리뷰 조회

### 3순위: 선택 자재 저장

현재 자재 선택은 프론트 Context에만 있고 새로고침 시 사라진다. 그러나 의뢰 ID가 생성되지 않으므로 지금 DB 컬럼이나 테이블부터 추가해도 실제 사용되지 않는다. 사용자 의뢰 생성 연결 후 아래 두 안 중 하나를 확정한다.

- 최소 테이블 우선안: `quote_request`에 테마와 벽지·바닥·조명 product ID 3개를 nullable FK로 추가
- 확장성 우선안: `request_material_selection` 1개 테이블로 작업 종류별 행 저장

현재 요구가 벽지·바닥·조명 3종으로 고정이고 테이블 수 최소화가 우선이므로 첫 번째 안이 더 적합하다. 다만 실제 저장 호출을 같이 만들 수 있을 때 Flyway V3로 추가해야 한다.

### 이미지 저장 판단

`request_image`는 이미 요청 ID, `FLOOR_PLAN`/`PHOTO`, URL, 표시 순서를 저장하며 소유자·참여 시공사 접근 검증과 테스트가 있다. 현재 요구 범위에서는 새 테이블이나 컬럼이 필요 없다. 문제는 테이블이 아니라 프론트 업로드 화면 연결 여부다.

## 의도적으로 보류한 변경

- 정산의 `partner` 명칭·관계 변경: 지급 주체·수수료·세금계산서 정책 미확정
- 견적 작성에 현장방문 완료를 서버 강제 조건으로 추가: 화면 설명은 그렇게 되어 있으나 담당자 API 테스트 흐름과 정책 확인 필요
- 견적 수정 이력의 새 행/버전 정책: 현재 `revision_count`와 다건 견적 설명이 완전히 일치하지 않음
- 채팅 목록 N+1 조회 최적화: 데이터 증가 전에는 동작하지만 규모가 커지면 집계 쿼리·페이지네이션 필요
- 목업 포털 전면 삭제: 담당자 작업 보호를 위해 실 API 전환이 끝난 페이지부터 제거해야 함

## 다음 작업의 완료 기준

- 새 의뢰 ID가 프론트 흐름 전체에서 유지된다.
- 복수 시공사 각각의 채팅·방문·견적 데이터가 섞이지 않는다.
- 견적 선택 후 다른 시공사는 더 이상 연락·수정할 수 없다.
- 선택 자재가 새로고침과 재로그인 후에도 같은 의뢰에서 복원된다.
- 프로젝트 완료 전 리뷰를 작성할 수 없다.
- 기존 DB 업그레이드와 빈 DB 생성이 모두 Flyway로 통과한다.
- 백엔드 전체 테스트, 프론트 전체 테스트와 빌드가 통과한다.

## 2026-08-07 실행 결과 갱신

위 문서의 `실제 연결 공백`은 계획 수립 당시 상태다. 이후 다음 항목을 구현하고 검증했다.

- 사용자 의뢰 생성과 request ID 세션 유지
- 도면·사진을 실제 의뢰에 연결
- 선택 테마와 벽지·바닥·조명 자재를 의뢰에 저장
- 추천 시공사 조회·상세·초대
- 시공사 의뢰 승인·거절, 방문, 견적 임시저장·제출, 프로젝트·리뷰·대시보드 실 API 연결
- Flyway V3로 선택 자재 컬럼 4개와 외래키 3개 추가
- 기존 DB 업그레이드와 빈 DB V1→V2→V3 재현 검증

따라서 현재 우선순위는 테이블 추가가 아니라 실제 로그인 계정으로 사용자→복수 시공사→견적 선택→프로젝트 완료까지 통합 시나리오를 수행하는 것이다. 외부 도면 AI 서버, 목업 ID 호환 분기, 견적 목록 N+1 조회, 리뷰 키워드 표시, 프론트 번들 분할은 별도 잔여 항목이다. 정산 정책과 방문 완료 전 견적 작성 강제 여부는 여전히 확정이 필요하다.
