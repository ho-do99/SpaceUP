# 백엔드 자재 카탈로그 전환 안내

## 한 줄 요약

프로젝트에서 이미 제외된 **자재업체 입점·상품 판매·재고·주문 기능**이 백엔드와 DB에 남아 있어, 실제 사용자 기능인 **테마별 자재 비교·추천**과 데이터 모델이 충돌했습니다. 이번 변경은 새 기능을 임의로 확장한 것이 아니라, 제거된 기획의 잔존 코드를 걷어내고 `material_product`를 읽기 전용 자재 카탈로그로 일치시키는 작업입니다.

## 왜 백엔드 코드를 수정했는가

기존에는 자재를 표현하는 모델이 두 개였습니다.

- `products`: 자재업체 회원이 상품을 등록하고 재고를 관리하며 주문받는 판매 모델
- `material_product`: 외부 판매처에서 확인한 자재를 비교·추천하기 위한 카탈로그 모델

현재 프로젝트 요구사항에는 자재업체 회원, 입점 승인, 재고 차감, 주문 처리 기능이 없습니다. 그런데 백엔드에는 다음 코드가 그대로 남아 있었습니다.

- `MATERIAL_VENDOR` 회원 역할과 관리자 승인 흐름
- `/api/products` 상품 등록·수정·재고 관리 API
- `material_orders` 주문 생성·배송 상태 변경 API
- 분석 추천 API가 빈 `products` 테이블을 조회하는 로직

그 결과 DB의 `material_product`에는 데이터가 있어도 추천 API는 항상 0건인 `products`를 조회했습니다. 이 상태에서 샘플 데이터만 바꾸면 화면과 백엔드가 서로 다른 테이블을 바라보는 문제가 계속됩니다. 따라서 데이터 수정만으로는 해결되지 않아 조회 경로와 잔존 도메인 코드를 함께 정리했습니다.

## 변경된 방향

### 1. `material_product`를 유일한 자재 카탈로그로 사용

`material_product`는 업체 소유 상품이 아니라 사용자가 비교하는 읽기 전용 데이터입니다.

- 공종: `WALLPAPER`, `FLOORING`, `LIGHTING`
- 테마: `MODERN`, `WOOD`, `WHITE`, `MARBLE`
- 가격 구간: `LOW`, `MID`, `HIGH`
- 판매처·모델·출처 URL·가격 확인 시점 보관
- 시공비는 자재 가격과 성격이 다르므로 저장하지 않음

기존 `grade`는 품질 등급처럼 오해될 수 있고 실제 근거가 없어서 제거했습니다. 대신 사용자가 요구한 테마와 비교 목적이 명확한 `theme`, `price_tier`로 교체했습니다.

### 2. 추천 API 주소와 응답 구조는 유지

기존 주소는 그대로입니다.

```http
GET /api/analysis/request/{requestId}/recommended-products
```

선택한 테마를 전달할 수 있도록 선택 파라미터만 추가했습니다.

```http
GET /api/analysis/request/{requestId}/recommended-products?theme=WOOD
```

`theme`을 보내지 않는 기존 호출은 `MODERN`을 기본값으로 사용합니다. 기존 프론트나 테스트가 깨지지 않도록 `productId`, `productName`, `category`, `unitPrice`, `quantity`, `amount`, `reason` 등 응답 필드명도 유지했습니다.

기존 `vendorName` 필드는 클라이언트 호환을 위해 당분간 남아 있지만, 값은 업체가 아닌 `brandName`과 동일하게 반환합니다. 새 코드에서는 `vendorName`에 업무 의미를 부여하면 안 됩니다.

### 3. 별도 읽기 전용 카탈로그 API 추가

```http
GET /api/material-products
GET /api/material-products?theme=WHITE
GET /api/material-products?theme=MARBLE&workType=FLOORING
```

등록·수정·삭제 API는 만들지 않았습니다. 가격과 출처 검증 절차 없이 운영 화면에서 카탈로그를 임의 수정하면 데이터 신뢰도가 낮아지기 때문입니다.

### 4. 제거된 코드와 테이블

- 백엔드 `domain/product` 판매 상품 도메인
- 백엔드 `domain/order` 자재 주문 도메인
- `ProductNotFoundException`, `OrderNotFoundException`, `InsufficientStockException`
- `MemberRole.MATERIAL_VENDOR`
- DB `products`, `material_orders`

제거 전 실DB 확인 결과 두 테이블 모두 0건이었고, `MATERIAL_VENDOR` 회원도 0명이었습니다. 실제 사용자 데이터 손실 없이 정리 가능한 상태를 확인한 뒤 제거했습니다.

관리자 대시보드 DTO의 `totalMaterialVendors`, `pendingMaterialVendorApprovals` 필드는 2026-08-07 잔존 요소 정리에서 제거했습니다. 현재 저장소에는 해당 필드를 사용하는 관리자 프론트가 없으며, 외부 관리자 화면이 있다면 변경 안내 문서를 확인해야 합니다.

## 샘플 데이터 기준

기존 60건은 `DEMO_MANUAL`, 가상 모델 코드, 미검증 상태여서 실제 추천 데이터로 사용할 수 없었습니다. 이를 전부 교체하고 다음 분포로 36건을 구성했습니다.

| 테마 | 벽지 | 바닥재 | 조명 | 합계 |
|---|---:|---:|---:|---:|
| 모던 | 3 | 3 | 3 | 9 |
| 우드 | 3 | 3 | 3 | 9 |
| 화이트 | 3 | 3 | 3 | 9 |
| 대리석 | 3 | 3 | 3 | 9 |
| 합계 | 12 | 12 | 12 | 36 |

제품명과 확인가는 월플랜, 오늘의집, 장판나라, IKEA Korea 판매 페이지를 기준으로 기록했습니다. 온라인 가격과 판매 상태는 변할 수 있으므로 `price_checked_at`과 `product_url`을 함께 저장합니다. 가격은 견적 확정가가 아니라 비교용 참고가입니다.

## DB 적용 전후 확인

이 프로젝트는 Flyway 의존성이 실제로 연결되어 있지 않으므로 SQL 파일이 자동 실행되지 않습니다. 반드시 백업 후 수동 적용해야 합니다. MySQL의 DDL은 암묵적 커밋이 발생하므로 단순 `ROLLBACK`으로 전체 복구되지 않습니다.

적용 후 확인 쿼리:

```sql
SELECT theme, work_type, COUNT(*) AS product_count
FROM material_product
GROUP BY theme, work_type
ORDER BY theme, work_type;

SELECT theme, work_type, price_tier, COUNT(*) AS product_count
FROM material_product
GROUP BY theme, work_type, price_tier
HAVING COUNT(*) <> 1;

SELECT COUNT(*) FROM material_product;
SHOW TABLES LIKE 'products';
SHOW TABLES LIKE 'material_orders';
SELECT user_role, COUNT(*) FROM user_account GROUP BY user_role;
```

정상 결과는 전체 36건, 각 `theme × work_type` 조합 3건, 각 `theme × work_type × price_tier` 조합 1건입니다. `products`, `material_orders`, `MATERIAL_VENDOR`는 없어야 합니다.

## 롤백

스키마 변경 전에 만든 전체 덤프를 복원하는 것이 유일하게 안전한 롤백입니다. 특히 `grade` 제거와 두 테이블 삭제는 데이터 정의 변경이므로 역방향 SQL을 즉석에서 작성하지 마십시오.

## 호환성과 테스트 원칙

- 기존 추천 API URL 유지
- 기존 추천 응답 필드 유지
- 테마 미전달 시 `MODERN` 기본값
- 프론트는 카탈로그 API 성공 시 실데이터 사용
- API 실패 시 기존 목업으로 폴백하여 담당자의 수동 화면 테스트를 방해하지 않음
- 기존 선택 ID가 새 카탈로그에 없으면 첫 상품으로 안전하게 재선택
- 관리자 대시보드의 업체 집계 필드는 0으로 유지

## 남은 주의사항

현재 DB의 `image_url`은 판매처 이미지의 무단 핫링크와 주소 만료 문제를 피하기 위해 비워 두었습니다. 프론트는 기존 카테고리 대표 이미지를 폴백으로 표시합니다. 실제 제품 이미지를 서비스에 노출하려면 판매처 이용 조건을 확인한 뒤 자체 저장소에 허용된 이미지를 보관하고 `image_url`을 갱신해야 합니다.

또한 `ddl-auto=update`는 운영 스키마 변경 이력을 보장하지 못합니다. 이번 작업과 별개로 Flyway 의존성과 베이스라인 전략을 정식 도입하는 것이 필요합니다.
