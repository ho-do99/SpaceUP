## 3. Flyway 기준선 도입

### 변경 이유

- 기존 `ddl-auto=update` 방식은 실행 시점마다 Hibernate가 DB를 변경하므로 팀원별 동일한 스키마와 변경 순서를 보장하기 어렵다.
- 현재 실DB 25개 테이블과 자재 기준 데이터 36건을 새 환경에서도 재현할 공식 기준선이 없었다.

### 코드·설정 변경

- Spring Boot 4용 `spring-boot-starter-flyway`와 MySQL Flyway 모듈을 추가했다.
- `V1__baseline_schema.sql`에 업무 테이블 25개의 기준 스키마를 작성했다.
- `V2__reference_material_catalog.sql`에 테마별 자재 36건을 작성했다.
- Hibernate를 `ddl-auto=validate`로 전환했다.
- Flyway clean을 비활성화하고 기존 DB 기준 버전을 2로 설정했다.
- 스키마 비교용 출력이 V1 파일을 덮어쓰지 않도록 출력 위치를 `build/schema-export.sql`로 바꿨다.
- 로컬 프로필에서는 의뢰 자동취소 스케줄러를 비활성화하고 기본·운영 환경에서는 기존처럼 활성화되게 조건부 설정을 추가했다.

### 백업

- `tmp/db-backups/spaceup-before-flyway-baseline-20260807-002746.sql`
- SHA-256: `DB5B0829837967F86C609D56E22444BC7D6A62078AF6E7D0B35EAC2CB86A0190`
- 크기: 60,246 bytes
- 덤프 완료 표식 확인

### 검증 결과

- 기존 실DB: V1/V2와 동등한 DB를 Flyway version 2로 baseline 처리하고 Hibernate validate·애플리케이션 시작 성공
- 새 빈 MySQL 8.0.46 DB: V1→V2 순차 적용, 업무 테이블 25개·자재 36건 생성, Hibernate validate·애플리케이션 시작 성공

## 4. 검증 중 자동취소 스케줄러 실행 사고와 복구

### 발생 내용

- 첫 Flyway 검증 실행에서 Spring Boot 4의 Flyway 자동설정 의존성을 잘못 선택해 Flyway는 실행되지 않았다.
- 동시에 비웹 검증 프로세스에서 기존 자동취소 스케줄러가 실행되어 의뢰 2~5의 상태가 `CANCELED`로 바뀌고 자동취소 알림 5건이 추가됐다.
- 원인은 검증 실행에서 스케줄러를 차단하지 않은 것과 프로세스 종료 감시 조건이 실제 로그와 맞지 않았던 것이다.

### 조사·복구

- 변경 전 전체 백업의 INSERT 데이터를 동일 세션의 임시 테이블로 불러와 실DB와 행 단위로 비교했다.
- 변경된 의뢰 2~5의 모든 컬럼을 백업값으로 정확히 복원했다.
- 백업 이후 스케줄러가 추가한 알림 ID 11~15만 선별 삭제했다.
- `request_contractors`를 포함한 관련 데이터에 추가 차이가 없음을 확인했다.

### 복구 후 상태

- 의뢰 상태: 1번 `CANCELED`, 2번 `NEW`, 3번 `NEW`, 4번 `APPROVED`, 5번 `NEW`
- 알림: 기존 10건
- 자재: 기존 36건
- 첫 실패 실행에서는 `flyway_schema_history`가 생성되지 않았다.

### 재발 방지

- Spring Boot 4 공식 Flyway starter로 의존성을 교체했다.
- 자동취소 스케줄러에 설정 기반 실행 조건을 추가했다.
- 로컬 프로필은 자동취소를 기본 비활성화했다.
- 이후 기존 DB와 빈 DB 검증은 스케줄러 비활성 상태로 다시 수행해 모두 성공했다.

## 5. 프론트·백 API 응답 계약 정합화

- 프론트가 의뢰 생성 응답을 객체로 예상하던 부분을 백엔드 실제 계약인 숫자 request ID로 맞췄다.
- 의뢰 수정·승인·거절의 성공 응답은 백엔드 계약대로 `data: null`을 허용하게 바꿨다.
- 이미지 연결 응답은 생성된 이미지 ID 숫자로 맞췄다.
- 의뢰 상세 응답에 이미 DB에 존재하던 보증금·현재 월세·목표 월세를 노출해 프론트 타입과 맞췄다.
- DB 스키마와 데이터는 변경하지 않았다.

## 6. 핵심 흐름 감사와 회귀 테스트 보강

### 확인한 흐름

- 한 의뢰에 여러 `request_contractors` 참여 행을 둘 수 있다.
- 시공사별 채팅과 현장방문이 request+contractor 조합으로 분리된다.
- 임대인은 여러 제출 견적을 비교하고 하나를 선택할 수 있다.
- 선택 시 선택 시공사는 `SELECTED`, 나머지 참여 시공사는 `CLOSED`가 되며 의뢰의 최종 contractor가 확정된다.
- 수락 견적은 프로젝트로 전환되고 착공·완료 요청·임대인 확인 후에만 리뷰가 가능하다.

### 추가 테스트

- 방문 완료된 선택 견적이 프로젝트로 전환되고 착공→완료 요청→임대인 완료 확인까지 진행되는 테스트
- 프로젝트 완료 후 임대인이 리뷰를 작성하고 시공사 평점이 갱신되는 테스트
- 여러 시공사의 방문 일정이 있으면 임대인 조회에 contractor ID가 반드시 필요한 테스트
- 기존 다중 시공사 견적 선택·채팅 격리 테스트와 함께 실행해 통과

### 과도한 변경을 막기 위해 보류한 부분

- 시공사 포털의 의뢰·방문·견적 화면 상당수는 아직 목업이다. 전체 실 API 전환은 담당자 화면 코드를 광범위하게 바꾸므로 이번 자동 작업에서 강제 전환하지 않았다.
- 화면 안내는 현장방문 완료 후 견적 작성 흐름이지만 백엔드는 승인만으로 견적 작성이 가능하다. 서버 강제 여부는 담당자 테스트 방식과 정책 확인 후 결정한다.
- 사용자 의뢰 생성 화면이 아직 `createRequest`를 호출하지 않으므로 선택 자재용 DB 컬럼을 먼저 추가하지 않았다. 사용되지 않는 스키마를 만드는 대신 선행 연결 공백을 명시했다.
- 상세 분석과 잔여 순서는 `Docs/전체계획_재수립_및_잔여작업.md`에 기록했다.

## 7. 전체 회귀 검증과 테스트 환경 분리

### 최초 전체 검증에서 발견한 문제

- Flyway 도입 후 MySQL 전용 V1 SQL을 H2 기반 Repository 테스트 2개 클래스가 실행해 9건이 실패했다.
- 제품 DB나 엔티티 오류가 아니라 테스트가 기존처럼 Hibernate `create-drop`을 쓰면서 새 Flyway도 동시에 실행한 설정 충돌이었다.
- 새 다중 방문 테스트 1건은 응답 DTO가 주소를 읽는데 테스트용 QuoteRequest에 Property를 넣지 않아 실패했다.

### 수정

- H2 Repository 테스트 2개에만 `spring.flyway.enabled=false`를 명시했다.
- 운영·로컬·신규 MySQL DB의 Flyway 동작은 그대로 유지했다.
- 다중 방문 테스트 데이터에 실제 응답 계약에 필요한 Property를 추가했다.

### 최종 결과

- 프론트엔드: 25건 통과
- 프론트엔드 프로덕션 빌드: 성공

## 8. 핵심 화면의 실 API 연결과 요청별 자재 선택 저장

### 변경 이유

- 기존에는 백엔드에 의뢰·다중 시공사·방문·견적·프로젝트 API가 있어도 프론트 주요 화면이 목업 데이터나 메모리 Context만 사용했다.
- 이 상태에서는 화면 테스트가 성공해 보여도 새로고침하면 진행 상태가 사라지고, 실제 DB에는 의뢰·이미지·자재 선택·견적이 남지 않는다.
- 화면 전체를 새로 작성하지 않고 숫자형 실 ID는 API, 기존 문자열형 목업 ID는 기존 목업으로 동작하게 분기해 담당자의 기존 화면 테스트 경로를 보존했다.

### 백엔드에서 건드린 부분과 이유

- 의뢰 수정 DTO와 응답에 선택 테마, 벽지·바닥·조명 자재 ID를 추가했다. 프론트에서 고른 세 자재를 같은 의뢰에서 복원하기 위해서다.
- `QuoteRequest`에 선택 테마와 세 `MaterialProduct` 관계를 추가했다. 별도 선택 테이블을 만들지 않고 현재 고정된 3종 자재 요구를 최소 테이블 구조로 저장하기 위해서다.
- 의뢰 수정 시 자재의 존재 여부, 활성 상태, 작업 종류, 선택 테마 일치 여부를 서버에서 검증한다. 프론트 값만 신뢰하면 벽지 자리에 조명 ID가 저장되는 데이터 오염이 가능하기 때문이다.
- 제출 전 `DRAFT` 견적을 수정하는 `PATCH /api/quotes/{quoteId}`를 추가했다. 기존 화면의 임시저장은 같은 견적을 계속 고쳐야 하지만 백엔드에는 생성·제출만 있어 저장할 때마다 새 견적 행이 생길 수 있었기 때문이다.
- 견적 수정은 `DRAFT` 상태에서만 허용하고 항목 교체 후 총액을 서버에서 다시 계산한다. 제출된 견적의 사후 변조와 프론트 합계 불일치를 막기 위해서다.

### 프론트에서 건드린 부분과 이유

- 매물 정보 입력에서 실제 의뢰를 만들고 생성된 request ID를 세션에 유지하도록 연결했다. 아파트는 주소·면적 확정 후, 기타 주택은 매물 정보 확정 시 생성한다.
- 도면과 현장 사진 업로드를 현재 request ID의 `request_image`에 연결했다.
- 테마와 벽지·바닥·조명 선택 product ID를 새로고침에도 유지하고 견적 요약에서 의뢰에 저장하도록 연결했다.
- 추천 시공사 목록·상세·초대 화면을 실 API에 연결했다.
- 시공사 포털의 의뢰 목록·상세·승인·거절, 방문 일정, 견적 임시저장·제출, 프로젝트 목록·상세·진행 액션, 리뷰 목록, 대시보드 집계를 실 API에 연결했다.
- 백엔드의 실제 응답 계약에 맞춰 의뢰·견적 생성은 숫자 ID, 수정·제출 성공은 nullable 응답, 리뷰 목록은 배열이 아닌 페이지 응답으로 수정했다.
- 실 API 전환 페이지에는 어댑터를 두어 백엔드 DTO를 기존 화면 모델로 변환했다. UI 레이아웃과 담당자가 작성한 목업 모델을 광범위하게 다시 쓰지 않기 위해서다.
- 기존 문자열형 목업 ID 경로는 남겼다. 숫자형 실제 ID에서는 DB/API를 사용하고 목업 ID에서는 기존 화면 테스트가 계속 가능하다.

### DB 변경과 Flyway V3

- `V3__request_material_selection.sql`을 새로 추가했다. 적용된 V1/V2는 수정하지 않았다.
- `quote_request`에 nullable 컬럼 4개를 추가했다: `selected_theme`, `selected_wallpaper_product_id`, `selected_flooring_product_id`, `selected_lighting_product_id`.
- 세 자재 ID는 `material_product.product_id` 외래키로 연결했고 조회 인덱스를 추가했다.
- 테마는 `MODERN`, `WOOD`, `WHITE`, `MARBLE` 또는 NULL만 허용한다.
- 업무 테이블은 25개 그대로이며 Flyway 관리 테이블은 업무 테이블 수에 포함하지 않는다.

### V3 적용 전 백업

- 정상 백업: `tmp/db-backups/spaceup-before-v3-clean-20260807-010929.sql`
- 크기: 61,487 bytes
- SHA-256: `22A686A2037D8573269185EFAEB3C6C7D819EEAE6148DC78BB9D3ADF7F21E467`
- `--no-tablespaces`로 생성했고 표준 오류가 비어 있으며 덤프 완료 표식을 확인했다.
- 첫 시도 파일은 계정의 `PROCESS` 권한 부족으로 tablespace 경고가 발생해 정상 백업으로 채택하지 않았다.

### 적용·재현 검증

- 기존 DB: Flyway V3 적용과 Hibernate validate 성공
- 기존 데이터 유지: 의뢰 상태 `1:CANCELED | 2:NEW | 3:NEW | 4:APPROVED | 5:NEW`, 알림 10건, 자재 36건
- 빈 MySQL 8.0.46 DB: V1→V2→V3 순차 적용 성공
- 빈 DB 결과: 업무 테이블 25개, 자재 36건, V3 선택 컬럼 4개, Hibernate validate와 애플리케이션 시작 성공
- 빈 DB 첫 재현 시도는 Windows의 공백 포함 MySQL 설치 경로 인용 오류로 서버가 시작되지 않아 DB 변경 없이 중단됐다.
- 두 번째 시도는 빈 비밀번호 환경변수가 PowerShell에서 제거되어 기본 비밀번호가 사용되는 문제로 인증 전에 중단됐다. 전용 임시 계정을 사용해 최종 검증을 다시 통과했다.

### 추가·변경 테스트

- 백엔드에 DRAFT 견적 수정·제출 후 수정 차단 테스트를 추가했다.
- 백엔드에 선택 자재의 테마·작업 종류 검증과 정상 저장 테스트를 추가했다.
- 프론트에 의뢰 draft/request ID 유지, 가격 문자열 변환, 견적 draft ID 유지·API 입력 변환 테스트를 추가했다.
- 견적 생성·수정·제출 API 계약 테스트를 실제 숫자 ID와 nullable 응답 기준으로 갱신했다.

### 담당자가 알아야 할 남은 한계

- 목업 ID 호환 분기는 의도적으로 남겼다. 실 API 전환이 확인된 뒤 페이지별로 제거해야 하며 지금 일괄 삭제하면 기존 담당자 화면 테스트가 깨진다.
- 도면 AI 분석은 외부 AI 서버 설정과 응답이 있어야 완료된다. 의뢰·도면 저장 연결과는 별개이며 AI 서버가 없을 때 분석 완료까지 보장하지 않는다.
- 시공사 견적 목록은 현재 배정 의뢰를 조회한 뒤 의뢰별 견적을 추가 조회한다. 데이터가 커지면 전용 목록 API나 페이지네이션이 필요하다.
- 리뷰 키워드의 한글 표시 매핑은 백엔드 enum 정책 확정 전이라 완전하지 않다.
- 프론트 메인 JS 청크는 약 751KB로 기능은 정상이나 라우트 단위 코드 분할이 필요한 성능 부채가 남아 있다.
- 정산 구조와 현장방문 완료 전 견적 작성을 서버에서 금지할지는 정책 미확정이므로 이번 변경에 포함하지 않았다.

## 9. AI 인테리어 이미지 생성 화면 실연동

### 발견한 문제

- 사진 업로드 후 생성 화면은 백엔드 API를 호출하지 않고 스피너만 표시했다.
- 결과 화면은 실제 응답이 아니라 저장소의 고정 샘플 이미지를 표시했다.
- 업로드 원본과 생성 결과는 파일 저장소에는 기록돼도 의뢰의 DB 이미지 경로로 연결되지 않았다.

### 변경 내용과 이유

- 프론트 생성 화면에서 Gemini 백엔드 API를 실제 호출하고 성공·실패·재시도를 처리했다.
- 업로드 사진은 `PHOTO`, 생성 결과는 `AI_GENERATED`로 기존 `request_image`에 연결했다.
- 결과 화면은 실제 전후 이미지 URL을 사용하고 세션 이동 중에도 결과를 유지한다.
- 생성 요청에만 75초, Nginx API 프록시에 90초 제한을 적용했다. 일반 API의 기존 15초 제한은 유지했다.
- AWS SDK 2.30의 자동 CRC 체크섬이 NCP 업로드에서 `AccessDenied`를 발생시켜 NCP 전용 클라이언트에 `WHEN_REQUIRED`를 명시했다.
- Flyway V4는 `request_image.image_type` enum만 확장한다. 업무 테이블 수는 25개로 동일하다.
- 상세 설명은 `Docs/2026-08-07_AI_이미지_생성_실연동_안내.md`에 남겼다.
