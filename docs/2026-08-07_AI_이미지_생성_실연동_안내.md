# AI 인테리어 이미지 생성 실연동 안내

## 왜 코드를 변경했는가

기존 프론트는 집 사진 업로드가 끝나면 `/analysis/simulation/generating`으로 이동했지만, 이 화면에서 백엔드 생성 API를 호출하지 않았다. 결과 화면 역시 고정 샘플 이미지만 표시했다. 따라서 스피너가 끝없이 돌았고 Gemini API 키와 서버가 정상이어도 실제 생성은 시작되지 않았다.

또한 업로드 원본은 Object Storage에만 저장되고 의뢰와 연결되지 않았으며, 백엔드가 만든 결과 파일도 DB 경로로 남지 않았다. 재배포 후 파일을 유지하는 것과 "어느 의뢰의 이미지인가"를 복원하는 것은 별개이므로 DB 연결이 필요하다.

## 프론트엔드 변경

- 사진 업로드 성공 후 현재 의뢰의 `request_image`에 `PHOTO`로 경로를 연결한다.
- 생성 화면에서 `POST /api/analysis/request/{requestId}/interior-images`를 실제 호출한다.
- 일반 API의 15초 제한을 바꾸지 않고 생성 요청에만 75초 타임아웃을 사용한다.
- React StrictMode 개발 환경에서 Gemini 요청이 두 번 실행되지 않도록 effect 시작을 지연하고 cleanup 시 취소한다.
- 성공하면 실제 업로드 사진과 생성 결과를 기존 전후 비교 UI에 전달한다.
- 결과 정보는 세션에도 보관해 결과 화면을 다시 열었을 때 고정 샘플로 바뀌지 않게 한다.
- 실패 시 무한 스피너 대신 오류와 재시도 버튼을 표시한다.

피그마 레이아웃, 색상, 정상 상태의 화면 구조는 변경하지 않았다.

## 백엔드와 DB 변경

- 기존 `request_image` 테이블을 그대로 사용하고 `image_type`에 `AI_GENERATED`만 추가했다.
- Gemini 생성 파일을 저장한 뒤 반환 경로를 현재 의뢰의 `request_image`에 자동 연결한다.
- Flyway `V4__ai_generated_request_images.sql`이 enum 값을 확장한다.
- 업무 테이블 수는 25개로 변하지 않는다.
- NCP S3 호환 문제를 막기 위해 Object Storage 전용 AWS SDK 클라이언트는 선택 체크섬을 `WHEN_REQUIRED`로 제한한다.
- Nginx `/api/` 프록시 제한은 90초로 설정해 백엔드 Gemini 읽기 제한 60초보다 먼저 연결이 끊기지 않게 했다.

## 기존 담당자 흐름에 미치는 영향

- 기존 평면도 `FLOOR_PLAN`과 집 사진 `PHOTO` 값은 그대로 유지한다.
- 기존 API URL과 응답 구조는 바꾸지 않았다.
- 결과 비교 컴포넌트는 URL을 전달하지 않는 기존 호출에서도 샘플 이미지를 사용할 수 있어 다른 화면 테스트를 깨지 않는다.
- DB 테이블 추가·삭제, 기존 데이터 수정·삭제는 없다.

## 배포 시 확인

1. DB 백업 후 새 백엔드를 실행해 Flyway V4 적용을 확인한다.
2. `flyway_schema_history`에서 version 4 성공을 확인한다.
3. 사진을 업로드하고 `request_image`에 `PHOTO`가 추가되는지 확인한다.
4. 생성 완료 후 `AI_GENERATED`가 추가되고 두 경로 모두 `/api/files/images/` 형식인지 확인한다.
5. 결과 화면에서 업로드 원본과 실제 생성 이미지가 표시되는지 확인한다.
