# 시공사 실데이터 시연 흐름 설계

## 목적

시연 계정으로 `의뢰 목록/상세 → 승인 → 채팅 → 방문 일정 → 평면도·사진 → 견적` 흐름을 끝까지 진행할 때 숫자형 실제 의뢰가 목업 데이터를 참조하지 않도록 한다. 임대인과 시공사 양쪽에는 DB에 저장된 회원 닉네임, 시공사 프로필, 의뢰 이미지, 방문 일정, 채팅, 견적 상태를 표시한다.

## 범위

포함 범위는 다음과 같다.

- 시공사 의뢰 목록과 상세
- 의뢰 승인 및 승인 완료 화면
- 임대인/시공사 채팅 목록과 채팅방
- 임대인 방문 일정 요청과 시공사 방문 일정 관리
- 시공사에서 확인하는 사용자 평면도와 공간 사진
- 시공사 견적 목록, 작성, 미리보기, 상세, 전송 완료 화면
- 승인 중복 호출 방지와 서버 측 멱등 처리

정산, 리뷰, 포트폴리오, 알림센터의 기존 목업 제거는 이번 범위에 포함하지 않는다. 비숫자형 `REQ-*`, `SP-*` 디자인 확인 경로의 목업도 유지한다.

## 기준 계정과 표시 규칙

첨부된 이미지는 시연 계정의 참고자료다. 계정별 표시명은 API와 DB가 최종 진실 공급원이며 프론트에 이메일, 비밀번호 또는 업체명을 하드코딩하지 않는다.

- 임대인 화면의 상대 시공사명: `ContractorProfile.companyName`, 없으면 회원명
- 시공사 화면의 상대 사용자명: `Member.name`을 담은 `landlordName` 또는 `ChatThread.counterpartName`
- 숫자형 ID나 `99번`, `100번`은 사용자명 대체 텍스트로 사용하지 않는다.
- 의뢰번호는 보조 정보로만 `requestCode`를 표시한다.

## 설계 원칙

### 실데이터와 목업의 경계

라우트 파라미터가 양의 정수이면 실제 의뢰다. 실제 의뢰에서는 API 실패나 누락 데이터를 목업으로 덮지 않고 로딩, 빈 상태 또는 오류 상태를 표시한다. 비숫자형 디자인 확인 라우트에서만 `contractorPortalMockData`를 사용할 수 있다.

공통 데이터 조합은 `useContractorRequest`와 `requestToContractorDetail`이 담당한다. 화면은 이 어댑터가 만든 `ContractorRequestDetail`을 소비하고 개별 화면에서 별도의 목업 상세를 다시 조회하지 않는다.

### 의뢰와 사용자명

`RequestResponse.landlordName`을 `ContractorRequest.customerName`으로 변환한다. 목록, 상세, 승인 완료, 채팅, 방문 일정, 평면도·사진, 견적 화면은 이 값을 사용자 닉네임으로 사용한다. 실제 의뢰에서 닉네임이 비어 있으면 `사용자`라는 중립적 빈값 표시를 사용하되 ID 기반 이름을 만들지 않는다.

### 승인 멱등성

프론트는 `participationStatus`를 보존해 `INVITED`일 때만 승인 버튼을 보여준다. 승인 요청 중에는 버튼을 비활성화한다. `APPROVED` 또는 `SELECTED` 상태로 상세에 다시 들어오면 승인 API를 호출하지 않고 기존 승인 완료/채팅 화면으로 이동할 수 있게 한다.

서버의 `RequestService.approve`는 참여 상태가 이미 `APPROVED` 또는 `SELECTED`라면 상태 변경, 알림 발송, `lastActivityAt` 갱신을 수행하지 않는다. 최초 `INVITED → APPROVED` 전이에서만 세 작업을 수행한다. 그 밖의 상태는 기존 상태 전이 예외를 유지한다.

### 채팅 활성화

`ChatThread.contactable`을 작성 가능 여부의 유일한 기준으로 사용한다. `INVITED`, `APPROVED`, `SELECTED` 참여자는 채팅 가능하고 `REJECTED`, `CLOSED`는 읽기만 가능하다.

숫자형 실제 의뢰의 시공사 채팅방에서도 다음 버튼을 표시한다.

- 미완료 방문: `현장 방문 일정 잡기` → `/contractor/requests/{requestId}/visit`
- 방문 완료: `방문 일정 확인` 및 `견적서 작성`

채팅방 헤더에는 `ChatThread.counterpartName`을 사용자 닉네임으로 표시하고 의뢰번호는 보조 정보로 표시한다. 메시지 작성기는 thread 로딩 중에는 비활성화하고 `contactable === true`일 때 활성화한다.

### 방문 일정

임대인 방문 일정 화면은 URL의 `contractorId`로 `getContractor`를 호출해 업체명, 활동 지역, 전문 분야, 상담 가능 상태를 표시한다. 고정된 `공간디자인 인테리어`, `광주 북구`, `리모델링 전문` 문구는 제거한다.

시공사 방문 일정 화면은 `getVisit(requestId)`와 `useContractorRequest(requestId)`를 조합한다. 실제 의뢰에서 `contractorDefaultVisitSchedule`, mock project, mock flow 상태를 fallback으로 사용하지 않는다. 일정이 없으면 `UNSCHEDULED`, 일정이 있으면 API의 날짜, 시간, 주소, 담당자, 메모, 변경 요청, 완료 시각을 표시한다.

임대인이 아직 일정 엔티티가 없는 상태에서 요청하려면 현재 sessionStorage 저장 대신 서버가 지원하는 흐름을 사용해야 한다. 기존 API 계약상 최초 일정 등록은 시공사 권한이므로 임대인은 채팅에서 날짜를 협의하고, 시공사가 등록한 뒤 변경 요청을 보낸다. 임대인 화면에서 일정이 없을 때는 날짜 저장을 성공으로 가장하지 않고 `채팅에서 시공사와 일정을 먼저 협의해 주세요` 안내와 채팅 복귀 동작을 제공한다.

### 평면도와 사진

`getRequestImages(requestId)` 결과를 다음 우선순위로 사용한다.

1. `FLOOR_PLAN` 업로드 이미지
2. `floorPlanVariantId`가 있으면 등록 평면도 preview API
3. 실제 의뢰에서는 평면도 없음 상태

`PHOTO`는 사용자가 업로드한 공간 사진, `AI_GENERATED`는 생성 결과로 표시한다. 실제 의뢰에서 저장 이미지가 없을 때 `floor-plan-preview.png`, 거실/주방/욕실/현관 목업 이미지를 표시하지 않는다. 이미지 URL은 `resolveApiAssetUrl`로 정규화한다.

### 견적

숫자형 실제 의뢰는 quote API 결과만 사용한다.

- 견적 목록: 현재 시공사가 작성한 실제 견적을 조회해 상태와 단계를 표시
- 작성/수정: `DRAFT` 생성과 저장, `SUBMITTED` 제출을 실제 API로 수행
- 미리보기/상세/전송 완료: route의 실제 quote 또는 request를 조회해 사용자 닉네임, 의뢰 정보, 금액, 유효기간, 항목을 표시
- `PRELIMINARY`와 `FINAL` 단계 및 방문 완료 전 최종 견적 제한은 서버 응답을 따른다.

실제 API 응답이 없으면 목업 견적을 대신 보여주지 않고 `작성된 견적이 없습니다` 또는 오류 상태를 표시한다.

## 오류 처리

- API 로딩 중에는 중복 액션이 불가능한 로딩 상태를 표시한다.
- 승인, 메시지 전송, 방문 일정 변경, 견적 저장/제출 실패는 현재 화면에 오류 메시지를 표시하고 사용자가 재시도할 수 있게 한다.
- 실제 의뢰의 일부 보조 API가 실패해도 다른 API 결과는 유지한다. 단, 목업으로 대체하지 않는다.
- 접근 권한 오류는 일반 빈 상태와 구분해 API 오류 메시지를 표시한다.

## 테스트 전략

모든 동작 변경은 실패 테스트를 먼저 작성한다.

- 어댑터: 사용자 닉네임, 실제 평면도 우선순위, 실제 이미지 없음 상태
- 승인: 최초 승인 1회만 상태/알림/활동 갱신, 재승인 부작용 없음
- 채팅: 실제 의뢰의 작성기와 방문 버튼 활성화, 종료 thread 비활성화, 사용자 닉네임 표시
- 방문 일정: 시공사 프로필 표시, 실제 일정 표시, 실제 일정 없음에서 목업 미노출
- 평면도·사진: 업로드 이미지 표시와 목업 미노출
- 견적: 숫자형 의뢰에서 API 결과 사용 및 mock fallback 금지

검증 명령은 다음과 같다.

- frontend: `npm run test:run`, `npm run lint`, `npm run build:dev`
- backend: `./gradlew clean test bootJar --no-daemon`
- 배포 설정: 기존 `deploy/tests/*.test.ps1` 및 shell 문법 검사

## 브랜치와 병합

구현은 최신 `frontend` 브랜치에서 진행한다. 완료 후 원격 `frontend`에 push하고, `develop`에 병합해 전체 검증 및 CI를 확인한다. 오류가 없을 때 `main`에 병합하고 원격 CI와 immutable 이미지 빌드를 확인한다. 강제 push는 사용하지 않는다.
