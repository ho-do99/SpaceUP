# 백엔드 다중 시공사 견적·채팅 전환 안내

## 왜 기존 코드를 수정했는가

SpaceUP의 확정된 업무 흐름은 한 의뢰에 여러 시공사가 참여하여 사용자와 각각 채팅하고 견적을 제출한 뒤, 사용자가 견적을 비교해 한 시공사를 최종 선택하는 방식이다.

기존 백엔드는 `quote_request.contractor_id` 한 칸을 견적 요청 단계부터 사용했다. 이 구조에서는 마지막으로 배정된 시공사 한 명만 의뢰·채팅·현장방문·견적에 접근할 수 있었다. 여러 시공사를 억지로 연결하면 모든 채팅이 `request_id` 하나에 섞여 경쟁 시공사의 메시지가 노출될 수도 있었다.

따라서 화면 기능을 추가하기 위한 임의 변경이 아니라, 확정된 업무 규칙과 개인정보 격리를 맞추기 위해 도메인 구조를 조정했다.

## 변경된 기준

- `request_contractors`가 견적 비교 단계의 참여 시공사들을 관리한다.
- 매칭 점수도 의뢰 공통값이 아니라 참여 시공사별 `matching_score`로 저장한다.
- `quote_request.contractor_id`는 더 이상 견적 요청 대상을 뜻하지 않는다. 사용자가 최종 선택한 시공사만 기록한다.
- `POST /api/requests/{requestId}/assign/{contractorId}` 경로는 유지한다. 동작 의미만 시공사 교체가 아니라 견적 참여 초대로 바로잡았다.
- 시공사가 참여를 승인하면 해당 시공사 전용 현장방문과 견적 작성 흐름이 열린다.
- 채팅과 현장방문은 `(request_id, contractor_id)` 단위로 분리된다.
- 사용자가 견적 하나를 수락하면 해당 시공사를 `SELECTED`, 나머지 참여 시공사를 `CLOSED`로 전환한다.
- 확정 후에도 탈락 시공사와의 과거 채팅·견적은 조회할 수 있지만 새 메시지는 보낼 수 없다.
- 최종 선택 이후에만 계약 전환과 시공 프로젝트 흐름으로 넘어간다.

## API 호환성

삭제하거나 경로를 바꾼 기존 API는 없다.

### 채팅

- 시공사 로그인: 기존처럼 `/api/chats/{requestId}/messages`를 사용하면 로그인한 시공사 방을 자동 선택한다.
- 사용자 로그인: 참여 시공사가 한 명이면 기존 호출도 동작한다.
- 사용자 로그인 + 여러 시공사: `contractorId` 쿼리 파라미터가 필요하다.
  - `GET /api/chats/{requestId}/messages?contractorId=5`
  - `POST /api/chats/{requestId}/messages?contractorId=5`
  - `POST /api/chats/{requestId}/read?contractorId=5`
- 채팅 목록 응답에는 방 식별을 위해 `contractorId`가 추가되었다. 기존 응답 필드는 제거하지 않았다.

### 현장방문

- 시공사 로그인은 기존 URL로 본인의 방문 일정을 조회한다.
- 사용자가 여러 시공사의 방문 일정을 조회할 때는 `contractorId`를 전달한다.
- 방문 일정 응답에는 `contractorId`가 추가되었다.

## 상태 의미

`request_contractors.status`:

- `INVITED`: 사용자가 견적 참여를 요청함
- `APPROVED`: 시공사가 참여를 승인함
- `REJECTED`: 시공사가 참여를 거절함
- `SELECTED`: 사용자가 최종 시공사로 확정함
- `CLOSED`: 다른 시공사가 선택되어 접촉이 종료됨

`quote_request.status`는 의뢰 전체의 큰 단계만 표현한다.

- 여러 시공사 검토 중: `REVIEWING` 또는 `QUOTE_REQUESTED`
- 최종 시공사 확정: `APPROVED`
- 실제 시공 시작: `IN_PROGRESS`
- 사용자 완료 확인: `COMPLETED`

## 담당자별 확인사항

### 백엔드

- 시공사 참여 여부를 `quote_request.contractor_id`로 검사하지 말고 `request_contractors`로 검사한다.
- 최종 계약·시공·리뷰처럼 낙찰자만 필요한 기능은 `quote_request.contractor_id`를 사용한다.
- 사용자용 다중 채팅 화면은 반드시 `requestId + contractorId`를 방 키로 사용한다.
- 수락 처리는 의뢰 행을 잠근 뒤 수행하므로 동시에 두 견적이 선택되지 않게 유지한다.

### 프론트엔드

- 기존 목데이터 화면은 이번 변경으로 강제 전환하지 않았다.
- 실API 연결 시 채팅 목록의 `contractorId`를 상세·전송·읽음 API에 그대로 전달해야 한다.
- `RequestResponse.contractorId`는 최종 선택 전에는 `null`인 것이 정상이다.

## 데이터베이스 적용

- 마이그레이션: `database/migrations/20260806_04_multi_contractor_quote_flow.sql`
- 적용 전 전체 DB 백업이 필요하다.
- 기존 단일 배정 데이터는 `request_contractors`로 이관한다.
- 이미 `ACCEPTED` 견적이 있는 데이터는 해당 시공사를 `SELECTED`로 보정한다.
- 기존 현장방문 데이터에 시공사를 연결할 수 없으면 마이그레이션은 삭제하지 않고 실패하도록 설계했다. 이 경우 원본 데이터를 먼저 확인해야 한다.

## 롤백 주의사항

이 변경 이후 한 의뢰에 여러 시공사 데이터가 쌓이면 기존 단일 `contractor_id` 구조로 완전 복귀할 때 어떤 시공사를 남길지 자동 판단할 수 없다. 따라서 롤백은 적용 전 백업 복원이 가장 안전하다.
