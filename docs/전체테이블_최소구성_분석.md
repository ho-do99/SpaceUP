# SpaceUP 전체 테이블 최소 구성 분석

## 1. 판단 기준

- 기준 화면은 Figma `SpaceUP_시공사 화면설계서_v2` 노드 `1199:2684`와 `SpaceUP_사용자 화면설계서_v2` 노드 `1077:8450`이다.
- `Docs/ERD`의 5개 이미지는 개념 설계 참고자료로만 사용했다. 해당 ERD는 기능별 데이터를 매우 세분화한 안이므로 그대로 구현하면 현재보다 테이블이 크게 늘어난다.
- 목표는 테이블 개수 자체의 최소화가 아니라, 현재 화면 기능과 데이터 무결성을 유지하면서 중복 도메인을 없애는 최소 구성이다.
- 자재 카탈로그는 유지하고 자재업체 회원·승인·재고·주문·정산 기능만 제거한다.

## 2. Figma에서 확인한 핵심 기능

### 사용자

- 아파트·빌라 정보 입력과 평면도 검색 또는 직접 업로드
- 공간별 AI 분석과 공간 정보 수정
- 벽지·바닥재·조명·주방장 등 자재 탐색 및 선택
- 시공사 추천, 여러 시공사 견적 요청·비교·최종 선택
- 시공사별 채팅과 현장 방문 일정 조율
- 주택 가치 상승 리포트와 최종 견적 반영
- 계약 이후 프로젝트 진행 확인, 완료 확인, 리뷰 작성
- 알림 확인

### 시공사

- 업체·담당자·전문 분야·시공 지역·공개 설정 관리
- 포트폴리오 등록·수정·삭제
- 의뢰 조회, 채팅, 현장 방문 일정 조율
- 공사·자재별 견적 항목 작성, 임시 저장, 제출, 수정, 유효기간 연장
- 선택된 견적의 계약 전환
- 프로젝트 일정·진행·완료 요청과 체크리스트
- 받은 리뷰 조회
- 정산 예정·보류·완료 내역과 명세서
- 알림 확인

## 4. 제거 권장 4개

| 테이블 | 판단 | 근거 |
|---|---|---|
| `boards` | 제거 | 데이터 0건, 현재 화면·엔티티·API 없음 |

## 5. 새로 필요하지만 현재 실DB에 없는 5개

| 테이블 | 필요 이유 |
|---|---|
| `apartments` | 사용자 화면의 아파트 검색과 주소·단지 정보 |
| `floorplan_variants` | 아파트별 여러 면적·평형 평면도 |
| `contractor_projects` | 계약 전환 후 일정·상태·완료 확인 |
| `project_checklist_items` | 프로젝트별 여러 체크리스트 항목 |
| `reviews` | 완료된 시공의 리뷰와 시공사 평점 |

Hibernate 자동 생성에 맡기지 않고 명시적 SQL 마이그레이션으로 생성해야 한다.

## 6. 새 테이블 없이 컬럼으로 보강할 항목

- 사용자 선택 자재는 별도 선택 테이블 대신 `quote_request`에 JSON 스냅샷 컬럼을 두는 안을 우선 검토한다. 선택 빈도가 낮고 의뢰 단위로만 조회한다는 전제다.
- AI 입력·결과 이미지는 별도 파일 자산 테이블 대신 `request_image.image_type`을 확장해 관리한다.
- 주택 가치 리포트는 `analysis_job`의 분석값과 수락된 `contractor_quote`를 조합해 생성하고 별도 리포트 테이블을 만들지 않는다.
- 고정된 인테리어 스타일은 `material_product.theme`과 의뢰의 선택값으로 유지하고 별도 스타일 테이블을 만들지 않는다.
- 시공사 서비스 지역·전문 분야는 현재 `contractor_profiles`에 유지하고 별도 서비스 테이블을 만들지 않는다.

## 7. 반드시 보강해야 할 기존 구조

- `settlements.partner_id`를 자재업체까지 포함하는 범용 파트너가 아니라 시공사로 명확히 제한한다.
- 정산이 어느 계약에서 발생했는지 추적할 수 있도록 수락 견적 또는 프로젝트 외래키가 필요하다.
- Figma의 정산 보류 상태에 맞춰 정산 상태에 `ON_HOLD`가 필요하다.
- `reviews.rating`은 DB에서도 1~5 범위를 보장해야 한다.
- `contractor_quote`는 의뢰·시공사별 중복 초안 정책을 명확히 하고 이에 맞는 고유키가 필요하다.
- 알림은 `(receiver_id, is_read, created_at)` 조회 인덱스가 필요하다.
- `phone_verification`과 `user_account`의 인증코드 컬럼은 가입 전·가입 후 인증 흐름을 구분하되 중복 저장을 줄이는 방향으로 정리해야 한다.
- `spring.jpa.hibernate.ddl-auto=update`는 모든 마이그레이션이 준비된 후 `validate`로 전환해야 한다.

## 8. 24개 공격적 통합안은 보류

`contractor_projects`는 `quote_request`와 1:1이며 두 테이블에 진행 상태와 시공 정보가 일부 중복된다. 이론적으로 프로젝트 날짜·상태를 `quote_request`에 합치고 체크리스트가 의뢰를 직접 참조하게 만들면 총 24개로 줄일 수 있다.

하지만 현재 `ProjectService`, 프로젝트 Repository·DTO·API·리뷰 완료 조건이 모두 별도 프로젝트 엔티티를 기준으로 구현돼 있다. 지금 합치면 백엔드 수정 범위가 넓고 담당자의 기존 프로젝트 테스트를 깨뜨릴 위험이 크다. 테이블 1개 절감을 위해 감수할 변경량이 과도하므로 현재는 25개 안전안을 권장한다.

## 9. 적용 순서

1. 실DB 전체 백업 및 해시 기록
2. 필수 5개 테이블 명시적 마이그레이션 작성·검증
3. 빈 레거시 4개 테이블 제거와 게시판 관련 잔존 설명 정리
4. 자재업체 관리자 응답·문구·DTO·정산 명칭 제거
5. 정산·리뷰·견적·알림의 제약과 인덱스 보강
6. 이미지 유형·선택 자재 저장 방식 보강
7. 전체 테스트 후 `ddl-auto=validate` 전환

## 10. 1순위 적용 결과

- `20260806_05_minimal_schema_alignment.sql`을 실DB에 적용했다.
- 필수 5개 테이블을 추가하고 데이터가 없던 레거시 4개 테이블을 제거해 권장안인 25개 테이블로 정렬했다.
- 중복 범용 일정 도메인인 백엔드 `schedule` 패키지도 제거했다. 현장 방문은 `site_visits`, 계약 후 공사 진행은 `contractor_projects`가 담당한다.
- 프로젝트·리뷰 업무 로직과 프론트엔드 코드는 수정하지 않았다.
- 백엔드 111건과 프론트엔드 23건의 테스트 및 프론트 프로덕션 빌드를 통과했다.
- 다음 순서는 자재업체 잔존 용어 제거와 정산 구조 보강이다. 이는 DB·백엔드·프론트 타입에 영향을 줄 수 있으므로 한 단계로 묶지 않고 영향 범위를 나눠 승인 후 진행한다.
