# 프론트 API 연동 현황 문서 관련 반영 안내

작성일: 2026-08-11
대상 브랜치: `backend` (push 완료)

프론트팀이 공유한 API 연동 현황 문서(계약 부족으로 보류된 항목들)를 확인하고 실제 코드와 대조한 결과와, 그중 실제로 작업한 내용을 정리했습니다.

---

## 1. 이번에 새로 만든 것

### 1-1. 이메일 변경/인증 (완전히 없던 기능)
휴대폰 인증과 동일한 목업 OTP 패턴입니다.

- `POST /api/member/me/email/verify-code/send` — 인증코드 발급 (목업: 실제 메일 미발송, 코드가 응답에 그대로 포함)
- `POST /api/member/me/email/verify-code/confirm` — `{code}` → 확인 시 `emailVerified=true`
- `PUT /api/member/{memberId}`로 이메일이 실제로 바뀌면 `emailVerified`가 자동으로 `false`로 초기화됩니다 (이름만 바뀔 땐 초기화 안 함).
- `MemberResponse`에 `emailVerified` 필드가 추가되었습니다.

### 1-2. 비밀번호 변경 (완전히 없던 기능)
- `PATCH /api/member/me/password` — `{currentPassword, newPassword}` — 현재 비밀번호가 틀리면 400.

### 1-3. 견적 수정요청 구조화
- `POST /api/quotes/{quoteId}/request-revision` 요청 바디에 `targetItemIds`(수정이 필요한 견적 항목 id 목록), `requestedAmount`(희망 조정 금액)를 선택적으로 추가할 수 있게 확장했습니다. 기존처럼 `note`만 보내도 동작은 그대로입니다.
- 응답(`ContractorQuoteResponse`)에도 `revisionTargetItemIds`, `revisionRequestedAmount` 필드가 추가되었습니다.

### 1-4. 아파트 평면도 카탈로그 시드 데이터
아파트 검색 API(`GET /api/floorplans/apartments/search`)는 이미 있었지만 카탈로그가 비어 있어 검색 결과가 항상 빈 배열이었습니다. local/dev 서버 기동 시 샘플 데이터가 자동으로 채워지도록 했습니다. 프론트 `mocks/apartments.ts`를 확인해서 그중 3곳(상무센트럴/상무리버뷰/상무스카이)은 이름·주소·면적(59/74/84㎡)을 그대로 맞췄습니다.

---

## 2. "계약 부족으로 보류"라고 되어있었지만 실제로는 이미 구현되어 있던 것

코드를 직접 확인한 결과, 아래 항목들은 이미 완전히 구현되어 있습니다. 계약이 부족한 게 아니라 프론트에서 아직 확인이 안 된 상태로 보입니다.

| 문서상 표기 | 실제 상태 |
|---|---|
| 시공사 프로필 저장 `PUT /api/contractors/me` | 완전 구현 (`businessRegistrationNumber`/`companyName`/`activityRegions`/`specialties`/`portfolioUrl`/`introduction`) |
| 담당자 저장 `/manager` | 완전 구현 (`managerPosition`/`consultationHours`) |
| 업체 공개설정 `/disclosure` | 완전 구현 (공개 여부 6개 boolean 필드) |
| 서비스정보 `/service-info` | 완전 구현 (`estimateMin`/`estimateMax`/`availableFromDate` + 검증) |
| 추천상품 `recommended-products` | 응답 DTO 14개 필드로 이미 완비 |
| 회원정보 수정 email/name | 이미 가능 (`PUT /api/member/{id}`) |

상세 요청/응답 필드는 전체 API 문서(`Spaceup_백엔드_전체_API_문서.md`) §1, §5 참고해 주세요.

**"API 함수만 준비, UI 없음"으로 표기된 7개** — 의뢰이미지삭제, 방문일정변경요청, 견적거절, 견적연장, 프로젝트생성(계약전환), 체크리스트 추가/수정, 완료확인 — 도 전부 백엔드 엔드포인트가 실제로 존재함을 확인했습니다. 프론트 UI만 연결하면 바로 동작합니다.

---

## 3. 삭제된 것

- **주택가치 상승 리포트 관련 필드**: `AnalysisJobResponse`에서 `depositIncreaseMin/Max`, `preliminaryDepositIncreaseMin/Max`, `preliminaryRentIncreaseMin/Max`를 삭제했습니다. 프론트 타입(`AnalysisJobResponse`)에 이 필드들이 선언은 되어 있었지만 실제로 읽는 컴포넌트가 없는 걸 확인했습니다 — 삭제해도 화면에 영향 없습니다. ROI 요약 카드용 `expectedRentIncreaseMin/Max`, `paybackPeriodMonthsMin/Max`는 그대로 유지됩니다.
- **`/api/schedules`(공사 일정) 도메인 전체 삭제**: `/api/projects`와 기능이 중복되어 사용되지 않던 코드였습니다. 공사 일정/진행 관련 기능은 `/api/projects`로 일원화되어 있습니다.

---

## 4. 여전히 필요하지만 이번에 안 한 것 (환경/데이터 이슈)

- **AI 평면도 실제 스캔**: `AI_FLOORPLAN_BASE_URL`이 가리키는 AI팀 서버가 실제로 떠 있어야 동작. 백엔드 코드 문제 아님.
- **AI Before/After(Gemini) 이미지 생성**: 코드는 실연동 완료. 배포 서버에 `GEMINI_API_KEY`만 설정되면 바로 동작합니다(현재 진행 중).

---

## 5. 참고 — 확인 안 하고 넘어간 것

- 사용자 프로젝트 목록/상세의 ID 체계(`requestId`/`quoteId`/`projectId`)와 사용자 리뷰 작성 시 필요한 `requestId` 매핑은 기존 그대로입니다(백엔드 코드 변경 없음) — 프론트 쪽에서 `ProjectResponse.requestId`를 활용하면 됩니다.
- 의뢰당 여러 시공사가 동시에 참여하는 구조(`request_contractors`)는 이번 작업과 별개로 이미 반영되어 있던 변경입니다. 자세한 내용은 `백엔드_다중시공사_견적채팅_전환_안내.md` 참고해 주세요.
